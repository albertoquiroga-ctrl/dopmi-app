# Video backend contract

This document describes the contract and operational gates, not an activation authorization. For the actual environment, deployment, provider configuration, QA and OFF/paused checkpoint, use [the current delivery checkpoint](../../../docs/mock-sync-current.md). The committed foundation is [20261019041400_integral_video_store_foundation.sql](../../migrations/20261019041400_integral_video_store_foundation.sql); [the migration history audit](../../../docs/migration-history-audit.md) records its remote mapping and deployed SQL comparison. Do not replay, rename or repair migrations to align timestamps. DEV deployment/configuration and completed QA do not establish production activation or authorization for another QA window.

POST `video-media`: `begin {parent_id,parent_version,purpose,request_key,bytes,file_fingerprint?}`; `status|playback|cancel {id}`; `review {id,parent_version,decision,note}`; admin `list`; anonymous `public_list {parent_id}`. Purposes: thanks, urgency, expense_evidence (always private), public_update, farewell. IDs for parents must refer to current real rescue records; version and ownership derive from PostgreSQL. `file_fingerprint` is optional/nullable in the SQL contract for compatibility; the mobile client supplies the file's SHA-256. `begin` is idempotent for the same immutable request tuple, including bytes and the fingerprint when supplied. Reuse the same tuple and `request_key` after network loss; never generate another automatically.

`begin` returns id/technical_state/moderation_state and, once created, upload_url. Use TUS HEAD/PATCH on that capability to resume the same upload. A 202 `upload_state: provisioning_unknown` means stop retrying creation and request operational reconciliation; Stream does not document idempotent create. Reconcile account assets using server-side asset_id metadata before any manual bind or cleanup. Never log upload capabilities, playback tokens or provider metadata. A local canceled/deleted asset must never be rebound.

`playback` returns hls/poster/expires_at, signed for 120 seconds, only after authoritative provider readback and database reauthorization. Anonymous playback is available only for approved media belonging to an approved visible parent snapshot. A delivered token can remain usable until expiration following withdrawal; no token is refreshed after withdrawal. New technical ready state never changes moderation. Review is separately version-checked and audited. Financial original evidence cannot be promoted to public media; explicit public_update is a distinct asset under a case.

Provider configuration must be verified for the target environment through its existing secure configuration: CLOUDFLARE_ACCOUNT_ID, CLOUDFLARE_STREAM_API_TOKEN, CLOUDFLARE_STREAM_WEBHOOK_SECRET and the independent DOPMI_VIDEO_WORKER_SECRET. Consult the checkpoint for actual DEV configuration; never copy or expose credential values in evidence. SUPABASE_URL, SUPABASE_ANON_KEY and SUPABASE_SERVICE_ROLE_KEY are platform-injected variables; reuse them rather than recreating reserved SUPABASE_ secrets. DOPMI_VIDEO_ALLOWED_ORIGINS must list exact admin browser origins. `DOPMI_VIDEO_ENABLED` defaults off. Private SQL settings also default off; change only in the authorized activation package, after provider, mobile and admin integrations pass. New cases then require a ready thanks clip at submission and an approved clip at publication; preexisting cases are grandfathered.

Webhook is POST `video-media/webhook`; verify_jwt must be false for this function because Stream does not carry Supabase JWT. User mutations still verify getUser plus PostgreSQL ownership. Webhook must pass HMAC/timestamp and server readback; replayed/late notifications never resurrect canceled/deleted assets. Do not configure the account-wide Stream webhook before checking any existing subscription (one per account).

Cleanup uses the separate POST `video-cleanup` endpoint (`/functions/v1/video-cleanup`), with `Authorization: Bearer <DOPMI_VIDEO_WORKER_SECRET>`. This independent server secret must contain at least 32 characters; app user tokens and the service-role key do not authorize this endpoint. `DOPMI_VIDEO_CLEANUP_ENABLED` defaults off and must explicitly equal `true` to drain work. The function has `verify_jwt = false` because its handler validates the separate worker secret. GET returns 405; a missing/wrong secret returns 401; a valid secret with cleanup disabled returns 503. Successful drains return only `{removed,failed}` counters (200, or 503 when a deletion failed), never provider IDs. Before enabling in any environment, verify both deployed functions, the audited migration, the authorized server-only scheduler and durable cleanup retries under the applicable approved package. The actual DEV scheduler and its paused/active state belong in the checkpoint, not an assumption that this README installs or enables a job. The outbox survives parent/account deletion and contains provider IDs only. Stream DELETE 404 is idempotent success. Alert on nonempty/failed cleanup tasks; reconciliation is required for a creation response lost upstream. Enable neither SQL nor Edge flags while that operational dependency is absent.

For a bounded authorized QA window, reserve time to cancel and close before its deadline. Normal closure must cancel/reconcile the same asset while the Edge video flag remains ON: `cancel` and `status` return 503 after video is OFF. After authoritative cancellation, turn media OFF, drain the durable cleanup task within the authorized window, then turn cleanup OFF and pause the reviewed scheduler job. Verify the terminal canceled/deleted state, null upload capability, empty queue and provider absence separately; never clear a task merely to obtain a passing result. At the hard deadline, media and cleanup must be OFF and the job paused even if work remains. Preserve the real ledger/queue, record the blocker, and obtain any further authorization separately; neither retries nor this README extend a window or implicitly reopen service.

Sources checked: Cloudflare direct creator uploads, resumable uploads, using webhooks, securing Stream; Supabase function JWT/Auth and RLS rules. The module uses signed-only TUS creation, maximum 60 seconds and technical file cap 200 MiB. Processing validates actual provider duration and rejects unsafe or overlong assets.
